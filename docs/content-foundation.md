# โครงข้อมูล Family JS

> Security update: สำหรับโปรเจกต์ใหม่ให้ใช้ migration `001` → `004` → `006` → `007` และข้าม `002`/`003` ซึ่งเป็นเดโมเก่าที่เปิดสิทธิ์กว้างเกินไป ดู [security-check.md](security-check.md) สำหรับการตรวจโปรเจกต์ที่ใช้งานอยู่

โครงนี้เตรียมเว็บสำหรับฐานข้อมูลโดยเก็บหน้าตาเดิมไว้: หน้าแรกยังเป็นตู้, หน้าหมวดยังมีธีมของตัวเอง, หนังสือยังอยู่บนชั้นและเปิดด้วยแอนิเมชันเดิม

## ส่วนที่ต่อเข้าหน้าเว็บแล้ว

- `lib/content/repository.ts` เป็นจุดอ่านข้อมูลของหน้าหมวดและบล็อก
- repository อ่านข้อมูลหนังสือและบทความจาก Supabase เท่านั้น; `lib/genres-data.ts` เก็บเฉพาะธีม และ `lib/blog-data.ts` เก็บชนิดข้อมูล
- หน้า `/genre/*`, `/blog/*` และส่วนบทความบนหน้าแรกอ่านผ่าน repository แล้ว; เมื่อมี backend ให้เปลี่ยน implementation ที่จุดนี้และแปลงข้อมูลเป็น `GenreThemeConfig` / `BlogPost` ก่อนส่งให้ component เดิม
- ธีม สี ชั้นหนังสือ แอนิเมชัน และตู้หน้าแรกยังอยู่ใน component/CSS เดิม
- ชั้นหนังสือแสดงได้สูงสุด 6 เล่มต่อชั้น; เล่มถัดไปขึ้นชั้นใหม่ในหมวดเดิมตามลำดับที่ repository ส่งมา

## ฐานข้อมูลที่เตรียมไว้

`supabase/migrations/202611230001_content_foundation.sql` มี `profiles`, `genres`, `books`, `reviews`, `genre_shelf_items` และ `blog_posts` พร้อม RLS ขั้นต้น

- `books` เก็บข้อมูลหนังสือ; `cover_path` ว่างได้เพื่อใช้ปกวาดด้วย CSS ที่มีอยู่
- `reviews` เก็บเนื้อหารีวิวและคะแนนทีละครึ่งดาว
- `genre_shelf_items` เลือกรีวิวเด่น ลำดับเล่มบนชั้น และค่าที่ใช้แสดงในธีมหมวด
- `blog_posts` เก็บบทความทั่วไปที่ไม่จำเป็นต้องผูกกับหนังสือ
- ผู้ใช้แก้โปรไฟล์ตัวเองได้ แต่ไม่ได้สิทธิ์แก้คอลัมน์ `role`; การตั้ง editor/admin ให้ทำผ่านช่องทางผู้ดูแลฐานข้อมูล

ภาพปกอยู่ใน Storage bucket `book-covers`; ตาราง `books` เก็บเฉพาะ `cover_path` รูปจริงจะแสดงบนหน้าหมวดและเมื่อเปิดหนังสือ หาก path ว่างจะใช้ปกจำลอง

รูปปกบทความและรูปที่แทรกในรีวิวหรือบล็อกใช้ bucket `book-covers` ที่มีอยู่แล้ว รูปปกบทความเก็บ path ใน `blog_posts.sections[0].cover_path` รูปจากเครื่องจะถูกย่อเป็น WebP หรือ JPEG ขนาดไม่เกิน 5 MB ก่อนอัปโหลด; บทความที่ไม่มีรูปปกยังใช้ภาพธีมเดิม

Migration `202611230004_secure_covers.sql` สร้าง bucket จำกัดชนิด/ขนาดไฟล์ และคืนสิทธิ์ตารางจากนโยบาย demo ที่เปิดกว้างใน `002` รวมถึงหยุดการให้บัญชีใหม่เป็น admin อัตโนมัติจาก `003` บัญชีที่เคยถูกปรับเป็น admin แล้วต้องตรวจสิทธิ์ด้วยตนเอง

## ลำดับเชื่อมระบบจริง

1. รัน migration ตามลำดับจนถึง `004` ใน Supabase project ที่ใช้จริง แล้วตรวจ `profiles.role` ของบัญชีที่มีอยู่; ให้สิทธิ์ editor/admin เฉพาะคนที่ต้องจัดการเนื้อหา
2. ตรวจ `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_ANON_KEY` ใน `.env.local` แล้วรีสตาร์ตเซิร์ฟเวอร์
3. ลองอัปโหลด WebP/PNG/JPEG จากหน้าแอดมิน บันทึกรีวิวและบทความ แล้วตรวจรูปปกบนหน้าหมวด หนังสือที่เปิดอ่าน การ์ดบล็อก และรูปในเนื้อหา
4. ตรวจ RLS ด้วยบัญชี reader, editor และ admin ก่อนเปิดใช้งานภายนอก

## ถ้าบัญชีเข้า `/admin` ไม่ได้

หน้า admin เปิดให้เฉพาะ `profiles.role` ที่เป็น `editor` หรือ `admin` การสมัครสมาชิกใหม่ได้ role `reader` ตามค่าเริ่มต้น ให้เจ้าของ Supabase project รันคำสั่งนี้ใน SQL Editor โดยเปลี่ยนอีเมลเป็นบัญชีที่ต้องการให้สิทธิ์:

```sql
insert into public.profiles (id, display_name, role)
select id, coalesce(nullif(raw_user_meta_data ->> 'full_name', ''), 'ผู้ดูแลระบบ'), 'admin'
from auth.users
where lower(email) = lower('your-email@example.com')
on conflict (id) do update set role = 'admin';
```

หลังรันแล้วให้รีเฟรช `/admin` บัญชีอื่นจะยังไม่ได้สิทธิ์เพิ่ม

ยังไม่รวมคอมเมนต์ ไลก์ บุ๊กมาร์ก สถิติยอดอ่าน หรือ ISBN autocomplete เพราะฟีเจอร์เหล่านั้นต้องออกแบบสิทธิ์และการดูแลเนื้อหาเพิ่มเติมก่อนเปิดใช้
